# AvNav: persistence and recovery on HALPI2

This document explains how to keep the AvNav, O-ChartsNG, and Signal K
changes persistent and how to restore them if a HaLOS update overwrites the
generated container configuration.

## What is permanent

The permanent source of the changes is the `apps/avnav/` directory in the
`halos-marine-containers` repository:

- `apps/avnav/Dockerfile` contains the ARM64 image customizations.
- `apps/avnav/docker-compose.yml` contains the persistent container settings,
  USB/HID access, image tag, and HTTPS routes.
- `apps/avnav/prestart.sh` contains runtime preparation that must happen when
  the container starts.
- `apps/avnav/metadata.yaml` contains the package version and web UI path.
- `apps/avnav/ochartsng/` contains the provider binaries required by the
  custom image.

These files must be kept in GitHub and included in the Debian package. The
generated Compose file on HALPI2 is only a deployment result and must not be
treated as the source of truth.

## What can be overwritten

The following may be regenerated by a HaLOS package update or container
recreation:

- `/var/lib/container-apps/marine-avnav-container/docker-compose.yml`
- Traefik routing labels generated from the package metadata
- The container itself and its writable runtime layer

Do not make the permanent fix by editing the generated Compose file. Such an
edit can disappear at the next package installation or service recreation.

AvNav application data under the container-apps data directory is separate
from the image and should normally be preserved, but it should still be
backed up before a recovery or reinstall.

## How to protect the installation

1. Keep the custom changes in the GitHub repository and merge the pull request.
2. Use a new, higher `version` in `apps/avnav/metadata.yaml` for later app
   changes.
3. Keep using the custom image tag, for example
   `stangsdal/avnav-daily:20260709-https9`, or publish an equivalent image to
   a registry that HALPI2 can access.
4. Build the ARM64 image and Debian package on the development Mac. Never
   compile or build on HALPI2.
5. Install updates through the HaLOS package workflow and restart the managed
   service with systemd.

## Backup before a manual recovery

On HALPI2, first create a backup of the persistent AvNav data and inspect the
Compose backups made by the package installer:

```sh
sudo tar -C /var/lib/container-apps -czf \
  /tmp/marine-avnav-container-data-$(date +%Y%m%d-%H%M%S).tgz \
  marine-avnav-container/data

sudo ls -lh /var/lib/container-apps/marine-avnav-container/*.before-*
```

Do not delete the backup until AvNav, O-ChartsNG, and Signal K have been
tested successfully.

## Recovery after an overwrite

### Preferred recovery: reinstall the package

Build the image and package on the Mac from the checked-out repository. Then
transfer the private image and package to HALPI2:

```sh
docker build --platform linux/arm64 \
  -t stangsdal/avnav-daily:20260709-https9 \
  apps/avnav

docker save stangsdal/avnav-daily:20260709-https9 | gzip | \
  ssh peter@192.168.1.181 'gunzip | docker load'

scp build/avnav-only/marine-avnav-container_20260709-12_all.deb \
  peter@192.168.1.181:/tmp/
```

Install the `.deb` using the normal HaLOS package mechanism. This regenerates
the Compose configuration from the repository-defined package contents.

Then restart and verify the managed service:

```sh
sudo systemctl restart marine-avnav-container
sudo systemctl is-active marine-avnav-container
sudo docker inspect --format \
  '{{.Config.Image}} {{.State.Status}} {{.State.Health.Status}}' avnav
```

### Emergency recovery: restore the last generated Compose file

If package installation is temporarily impossible, identify the most recent
installer backup:

```sh
ls -lt /var/lib/container-apps/marine-avnav-container/docker-compose.yml.before-*
```

Restore it only as a temporary measure, then restart the managed service. The
restored file is not a permanent fix; reinstall the corrected package as soon
as possible.

## Functional checks after recovery

Confirm all three browser-facing routes:

```sh
curl -kI https://halos.local:4431/viewer/avnav_viewer.html
curl -kI https://halos.local:4431/ocharts/static/index.html
curl -kI https://halos.local:4430/
```

In the AvNav UI, verify:

- O-ChartsNG is connected.
- The SG-Lock USB/HID dongle is detected.
- Downloaded charts can be opened.
- Signal K opens through `https://halos.local:4430/`.
- The browser console no longer shows blocked HTTP frames or WebSockets for
  the working integrations.

If the dongle is not detected, check the device on HALPI2 and the container
settings before changing application code:

```sh
ls -l /dev/hidraw*
sudo docker inspect avnav --format '{{.HostConfig.Privileged}}'
sudo docker logs --tail 200 avnav
```

The intended permanent workflow is therefore:

```text
GitHub source -> ARM64 image/package built on Mac -> HaLOS package install
-> generated Compose -> managed systemd service on HALPI2
```
